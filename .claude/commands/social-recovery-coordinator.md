Do not treat the provisional task cut as immutable, and do not let an unfinished chapter block work that is ready.

Optional argument: `$ARGUMENTS` names a task id, a wave, or an action (for example `PT-035`, `round 1`, `status`). With no argument, reconstruct the board and give the update.

## Rules the code keeps

- Screens build and test against the SDK doubles (PT-035) until the SDK lands, and import only the extension's own client layer (PT-038), never the doubles directly.
- While no SDK package exists, the extension's own client for the deployed contracts lives in `shared/client/kit`, built against the contracts' ABIs (M-7 served the setup flow; the recovery side is M-8's). The build-time variable `SOCIAL_RECOVERY_SEPOLIA_DEPLOYMENT` switches it on: with no value everything behaves as on the doubles. A member a flow does not yet serve refuses as not served and never falls back to the doubles. No test reaches a network, and neither a node's URL nor a deployed address appears in production code. An encoding the SDK's documents leave open is settled by read and simulation calls against the deployment before it is written, and the PR records the experiment.
- Code lives under `src/web/modules/social-recovery/<lane>/...`; the task file names the exact folder. Records live in local storage, never in a background controller (D-310). Ceremonies that die on focus loss run in a full tab through `tab.html` and `TabOnlyRoute`, never in the action popup (D-316).
- Shared files (`MainRoutes.tsx`, the route constants, `routesConfig.ts`, `en.json`, `jest.config.js`, `webpack.config.js`, `.eslintrc.js`, `.gitmodules`, the manifest) change only in the setup task, so parallel PRs do not collide. The one exception is a task's single `<Route>` line in `routes/SocialRecoveryRoutes.tsx`. If a task needs a shared change, stop and ask.
- Strings go into the i18n table and follow `design/ux-copy.md`; the banned words are `policy`, `proof`, `relayer`, `EIP-712`, `atomic`, `Protected`, `your people`, `full wallet password`.
- The proof of concept D-316 schedules ran on 2026-09-29 in a parallel session, on the throwaway branch `poc/d316-schedules` (its note under `poc/d316/`); PT-042 and PT-051 consume its answers as data, and the owner rules in the coordinator's chat. Where an owner ruling is open, a task builds what the ux chapter says and records the assumption in the PR description (owner, 2026-09-29).
- A task's `check: fuzz` has no runner here; the owner decides what a high-risk task's deeper test set is. Do not invent one.
- A screen that sends a write keeps the save's property (PT-051, owner's rulings of 2026-10-01 and 2026-10-02): it never shows the write as done, and never wipes its records, unless the receipt landed and the after-write read agrees for that same run; it never sends twice for one intent, across tabs, reloads and account switches; it never says nothing was sent for a send that can still land. No decision rests on a clock read taken after an await with no limit. The account's own key pays every recovery write of the account.
- Code, comments, test names and file names never reference the design documents: no decision ids (`D-nnn`), task ids (`PT-nnn`), invariant ids (`I-nn`), copy-rule ids (`UXC-n`), frame ids, `cut-q-n`, design file names or `docs/social-recovery/...` paths. A comment states the rule in plain words or is not written. The design documents are deleted before the last merge to main.
- No README files inside `src/web/modules/social-recovery/`. The rules agents follow live in `CLAUDE.md`. No overhead documentation and no comment in a shared file beyond the file's own style.
- Tests check behaviour. A test that only restates a declaration (a type, an `as const` list, an export) is not written.
- Types live apart from logic: each folder keeps its `type` and `interface` declarations in one `types.ts` (a subfolder with code of its own keeps its own), code files import them, `sdk-interfaces/` is types only and keeps its own files. A value our own code produced is typed, never parsed: `unknown` and guards only at a real boundary; an exported guard with no caller is deleted.
- Value helpers come from viem (address, hex, units, constants, typed-data recovery, the `Address` and `Hex` types, a custom account for a signer); ethers stays at the provider boundary (the extension's `RPCProvider`, its receipts, errors and `Interface`). No helper is written where viem, ethers or the repo already has one; a review round checks every PR for duplicated helpers.

## Agents per task

You stay on the model this session was started with and do not implement, test or review yourself. Every change to a PR after its first review goes the same way: a fresh implementer in an isolation worktree on `wip/<task>-impl-rN` cut from the task branch (explicit `git add` of the lane only, never a push), a tester on `wip/<task>-tests-rN` cut from the implementer's hash where a test changes, a fresh read-only reviewer in the tester's worktree with a verification pass by the same reviewer after fixes; a copy-only change may skip the reviewer with the coordinator inspecting the test diff. A small, exactly specified fix goes to one small agent, and the reviewer or verifier who found it verifies the commit. ## Runs against deployed contracts

The recovery contracts are deployed on a fork of Sepolia; its RPC, explorer, addresses and the `.env` line are in the README's section "Account recovery: manual test against a fork", which is also the script of the owner's manual test. A run that sends a transaction needs the owner's word for that run. It is done by an agent, never by the coordinator, in a build made for the fork and a fresh browser profile; the agent proves the page talks to the fork before the first send (the bundle holds the fork's host, the block number, the manager's code), sends only through the wallet's own sign screen with the account's own key as the payer, and never through a bundler, a paymaster or a relayer. The test wallet's keys are the same in every run and the owner funds them: when a key is short, stop and give him the address and the amount; never call a fork's balance cheat method. The fork keeps Sepolia's chain id, so a transaction signed for it is also valid on Sepolia: test wallets only. After a save, check the chain with read calls (the state, the authorization, the commit's log, the commitment built by hand) and prove the next step by simulation before any screen for it exists. No secret, seed or password goes into a report, a commit, a screenshot of an unlock screen or a file inside a repository.

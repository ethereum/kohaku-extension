# Proof of concept D-316, 2026-09-29

The proof of concept the ux chapter schedules in D-316 before the minimal setup's tasks materialize. It answers four questions about the Kohaku extension: whether the create door makes an Ambire v2 smart account by default, whether the extension deploys a counterfactual account inside the arming batch, whether the create door's picker exists, and which signing paths fail for a key at privilege value `1`. Run on 2026-09-29 by the coordinator session of the implementation, with subagents that read the code and drove the build.

Sources. The Kohaku extension at `dev/wonderland` 2f91323db on `defi-wonderland/kohaku-extension`, with `src/ambire-common` (the account library, `ethereum/kohaku-commons`) at 29227cc. A production build of that revision (`yarn build:web:webkit`, exit 0) driven in headless Chromium 140 with Playwright for the create door and the import door. The Sepolia testnet read through a public RPC with `eth_getCode`, `eth_call` and `eth_estimateGas` only; the session's policy refused a probe that sends transactions, so no transaction was sent and no test ETH was spent. The fork's branch `wonderland/recovery-v0` (June 2026, 13 commits) as evidence of an earlier prototype. The probe scripts and their raw results sit on the throwaway branch `poc/d316-schedules` under `poc/d316/`, never merged.

A line reference below is `path:line` at those revisions; extension paths are relative to the extension root, library paths to `src/ambire-common`.

## 1. Does the create door make an Ambire v2 smart account by default?

**No.** The create door adds one basic account, the key at `m/44'/60'/0'/0/0`. It derives a counterfactual Ambire v2 smart account beside it and never adds it. No flag turns a smart-account default on.

Evidence in the code:

- The create door goes to `createSeedPhrasePrepare` (`src/web/modules/auth/screens/GetStartedScreen/GetStartedScreen.tsx:61-63`), which makes a 12-word phrase on the BIP-44 template `m/44'/60'/0'/0/<account>` (`.../CreateSeedPhrasePrepareScreen.tsx:80-88`, `src/consts/derivation.ts:6`), then to the write screen, which hands the phrase to the picker controller (`.../CreateSeedPhraseWriteScreen.tsx:63-73`, handler `src/web/extension-services/background/handlers/handleActions.ts:128-132`).
- The picker controller's `init()` runs with `shouldAddNextAccountAutomatically` at its default `true` (`src/controllers/accountPicker/accountPicker.ts:60`, `:419`, `:433-438`). `selectNextAccount()` takes the first account on the page that is not imported, not linked and not a smart account (`accountPicker.ts:970-975`), and `addAccounts()` adds it.
- Each slot derives three things (`accountPicker.ts:1056-1123`): the basic account at the slot index, a second key at the index plus 100000 (`src/consts/derivation.ts:57`, `SMART_ACCOUNT_SIGNER_KEY_DERIVATION_OFFSET`) kept only as the smart account's key, and the smart account itself from `getSmartAccount([{ addr: smartAccKey, hash: dedicatedToOneSAPriv }])` (`accountPicker.ts:1093-1095`). The smart account's privilege value is `2` (`src/interfaces/keystore.ts:104-105`), not `1`.
- `getSmartAccount` returns a counterfactual record: the address is CREATE2 from the factory `0x26cE6745A633030A6faC5e64e41D21fb6246dc2d`, salt `0` and the proxy bytecode that stores the initial privileges (`src/libs/account/account.ts:77-98`, `src/libs/proxyDeploy/deploy.ts:37-60`); `creation` carries `factoryAddr`, `bytecode` and `salt`. Nothing deploys it. `isSmartAccount` is `!!account.creation` (`account.ts:191`).
- The selected-account default prefers a smart account when one exists (`account.ts:200-207`, `src/controllers/main/main.ts:294`), but on create none exists, so the basic account is selected.
- The private-key import derives no smart account at all (`accountPicker.ts:1056`).

Observed in the running extension:

The run `poc/d316/runtime/run1-create.js` (results in `results/run1-create/`, a `steps.json` with every route and screenshot) went through the create door in a fresh profile: `/get-started`, `/create-new-recovery-phrase`, `/backup-recovery-phrase`, `/keystore-setup`, `/account-picker`, `/account-personalize` ("Added successfully", "Account 1"), `/wallet-setup-completed`, `/dashboard`. The dashboard shows one account, `0x747816823A830B3bc1Fe7bc7d73a2D96Ef0B7A22`, badged "Internal", with no basic, smart or deployment badge. The storage dump (`accounts-after-onboarding.json`) holds one account record with `creation: null`, `associatedKeys` equal to its own address and `initialPrivileges: []`, and one keystore key of type `internal` with `dedicatedToOneSA: false`. No smart account record exists anywhere in storage, so there is no `creation` object to read. After onboarding, "Add account" from the account list and from settings offers only "Add from stored recovery phrases"; that path opens the picker and adds the next basic account (slot 2) on its own, before any button is pressed (`accounts-after-add-more-exploration.json`). The build of `dev/wonderland` crashed on every route as built; see the finding after the four questions.

## 2. Does the extension deploy a counterfactual account inside the arming batch?

**Yes on every route the library builds, and the route decides whether deployment and calls are atomic. On Sepolia, as the wallet configures it, only one route exists for a v2 smart account, and the wallet's sign screen refuses the arming batch before any route is reached.**

How the first operation of an undeployed account is built:

- An undeployed account is detected deployless: an `eth_call` runs `AmbireAccountState.sol:43-55`, which simulates the factory deploy when the address has no code and reads nonce and privileges from the simulated contract; the result lands in `accountState.isDeployed` (`src/libs/accountState/accountState.ts:113`, `src/interfaces/account.ts:38-55`).
- Route "another EOA pays" (`byOtherEOA`): one transaction to `AmbireFactory.deployAndExecute(bytecode, salt, calls, signature)` (`src/libs/broadcast/broadcast.ts:27-52`). The calls are `getSignableCalls(op)`, every call of the operation including self-calls (`src/libs/accountOp/accountOp.ts:162-167`). The factory deploys and then runs `execute` in the same transaction (`contracts/AmbireFactory.sol:44-53`; `deploySafe` skips the CREATE2 if code exists, `:100-120`). `execute` checks the signature, runs the batch, and reverts the whole transaction if a call reverts (`contracts/AmbireAccount.sol:140-172`, `:219-245`). Deployment and arming calls are atomic. The signature is the key's EIP-712 `AmbireOperation` signature over the execute hash with nonce `0` (`src/libs/signMessage/signMessage.ts:475-496`).
- Route "bundler" (`byBundler`, ERC-4337 v0.7, EntryPoint `0x0000000071727De22E5E9d8BAf0edAc6f37da032`): the deployment goes in `initCode` as `deployAndExecute(bytecode, salt, [setAddrPrivilege(EntryPoint, 0x7171)], entryPointSignature)` (`src/libs/userOperation/userOperation.ts:142-154`, `:46-57`, `:186`), and the user's calls go in `callData = executeBySender(calls)` (`src/controllers/signAccountOp/signAccountOp.ts:1631-1634`). The arming calls ride in the same user operation, in its execution phase, not inside `initCode`. The first bundler deploy asks the key for a separate EIP-712 authorization (`signAccountOp.ts:1869-1883`, shown as "Step 1/2 preparing account").
- Route "relayer" (`byRelayer`): the wallet posts the calls and the signature to `/identity/{addr}/{chain}/submit` (`src/controllers/main/main.ts:2003-2020`); the relayer runs `deployAndExecute` server side (`contracts/AmbireFactory.sol:35-36`).
- The route choice for a v2 account: a payer other than the account gives `byOtherEOA`; an ERC-4337 network gives `byBundler`; anything else gives `byRelayer` (`src/libs/account/V2.ts:104-113`). The fee options offered: the account's own native token always, a listed basic account's native token when it has a balance, tokens only with a paymaster or a relayer (`V2.ts:44-72`). The payer candidates are the wallet's non-smart listed accounts (`src/controllers/estimation/estimation.ts:158-167`).
- Sepolia, in the wallet's testnet mode (`main.ts:270`): `erc4337.enabled: false`, `hasPaymaster: false`, `isSAEnabled: false`, `hasRelayer: false`, `areContractsDeployed: true`, `hasSingleton: true` (`src/consts/testnetNetworks.ts:20-47`). So for a v2 smart account on Sepolia the bundler route does not exist, the account-pays option goes to a relayer the network does not have, and the one route that can land is a listed basic account paying through `deployAndExecute`.
- A self-call in the batch: `setAddrPrivilege` requires `msg.sender == address(this)` (`contracts/AmbireAccount.sol:97-99`), which a call inside `executeBatch` satisfies. But the sign controller's validator refuses any operation with a call whose `to` is the account itself, with the title "A malicious transaction found in this batch." and the code `CALL_TO_SELF` (`src/controllers/signAccountOp/signAccountOp.ts:349-358`). An arming batch that writes the account's privilege table is such a batch. The recovery-v0 prototype hit the same refusal and exempted the `setAddrPrivilege` selector `0x0d5828d4` in its library bump (`wonderland/recovery-v0`, commit 277d61723, library 250bcab83 `signAccountOp.ts:350-368`); that change is not in 29227cc.
- The EIP-7702 case of a listed basic account: with two or more calls and no delegation yet, the wallet signs a type-4 transaction whose authorization list delegates the EOA to `0x5A7FC11397E9a8AD41BF10bf13F22B0a63f96f6d` and whose data is `executeBySender(calls)` on the EOA itself (`src/libs/account/EOA7702.ts:130-158`, `signAccountOp.ts:1815-1834`, `broadcast.ts:125-133`, `main.ts:1870-1872`). Delegation and calls are atomic there too. The same validator refuses a self-call there as well.

What the recovery-v0 prototype found on Sepolia (evidence, not a base): its first design was one batch of five calls on the account (three contract deploys, a bind, and `setAddrPrivilege(adapter, 1)`); the estimator under-counted the CREATE2 deploys (about 230k estimated against more than 940k used) and the batch ran out of gas, so the prototype split activation into two operations (commit 3a64b9b1f); on a 7702-delegated EOA a call with no `to` became a plain EOA `CREATE` at a nonce address, so the deploys moved to explicit `SINGLETON.deploy` calls (commit 667211493). The prototype never used the Ambire factory and never deployed a counterfactual account.

Observed on Sepolia (read-only):

The probe `poc/d316/sepolia-readonly/probe.js` (results in `results.json` and `results.md` beside it) built an account the way the picker does, with fresh random keys, one initial privilege `{ keyA: 2 }`, salt `0` and the wallet's proxy bytecode, and simulated the wallet's own first operation with `eth_call` and `eth_estimateGas` through `https://ethereum-sepolia-rpc.publicnode.com`.

- Every contract the route needs holds code on Sepolia: the factory (2630 bytes), the account implementation `0x0F2AA7bcda3d9D210dF69a394b6965CB2566c828` (9552 bytes), the 7702 implementation (11162 bytes), the EntryPoint v0.7 (16035 bytes) and the singleton (308 bytes).
- `deployAndExecute(bytecode, 0, [setAddrPrivilege(keyB, 1), setAddrPrivilege(keyC, H), setAddrPrivilege(keyD, 1)], signatureOfKeyA)` from a random sender returned the computed CREATE2 address and estimated at 218423 gas. One transaction deploys the account and writes three privileges; the calls to the account itself pass inside the batch. The signature that works is the one the wallet builds, `AmbireOperation(account, keccak256(abi.encode(account, chainId, nonce 0, calls)))` in Standard mode; the typed-data form the repo's Solidity source describes (`AmbireExecuteAccountOp`) reverts `INSUFFICIENT_PRIVILEGE`.
- The implementation on Sepolia is not the repo's source: its runtime differs from `contracts/compiled/AmbireAccount.json` in 2999 bytes, it keeps `privileges` at mapping slot `0` where the source uses a named storage position, and its `execute` refuses an unprotected signature with `SV_USED_UNBOUND` where the source allows one. The wallet's client code matches the deployed contract, not the `.sol` in the tree.
- The account's EntryPoint privilege reads `0` after such a batch, so the bundler route would need the activator call the wallet adds only on ERC-4337 networks.

Observed in the running extension:

No smart account can be reached from the extension's screens (question 3), so no smart account operation could be opened. For the listed basic account of the test wallet on Sepolia (`run2b-sign-screen.js`, `results/run2b-sign-screen/`), a transfer of 0.0001 ETH to another address of the same phrase reached the estimation sheet inside the transfer screen: "Pay fee with", speed "Fast", a fee of 0.000042 ETH on Sepolia, and one fee option only, "With fee tokens from current account", ETH on Sepolia. ## 3. Does the create door's picker exist?

**Yes, and it opens on create.** The delta recorded in the PT-042 task file is half right: the picker controller does auto-add the first non-smart account (`accountPicker.ts:970-975`), but the picker screen is not skipped on create in Kohaku. The fork's commit 18e58b520 of 2026-03-20 ("feat: improve onboarding flow (#226)") sends both create and seed import to `account-picker`, then `account-personalize` (`src/common/modules/auth/contexts/onboardingNavigationContext/onboardingNavigationContext.tsx:130-154`). Upstream Ambire went to `account-personalize` directly for non-hardware flows, which is where the delta's wording comes from.

- The screen's hook dispatches `MAIN_CONTROLLER_ACCOUNT_PICKER_INIT` (`src/web/modules/account-picker/hooks/useAccountPicker/useAccountPicker.ts:42-45`); the controller adds the first basic account before the holder acts. The screen's title on create reads "Import accounts from recovery phrase" (`AccountPickerScreen.tsx:100-101`), since the sub-type is `seed`.
- The list shows basic accounts only: `state.accountsOnPage.filter((a) => !a.isLinked && !a.account.creation)` (`src/web/modules/account-picker/components/AccountsOnPageList/AccountsOnPageList.tsx:72-77`). The "Smart accounts" section and the linked-accounts notice are commented out (`:376-453`, `:80`). No smart-account toggle exists.
- The button reads "Import accounts" when something is selected, else "Continue" (`AccountPickerScreen.tsx:59-64`, `:154-160`); on a fresh phrase it adds nothing beyond the auto-added basic account (`accountPicker.ts:851-867`).
- The import door: "Import existing account" goes straight to the seed phrase import (`GetStartedScreen.tsx:65-67`); the selector offers only "Recovery phrase" (`ImportExistingAccountSelectorScreen.tsx:65-71`; private key, hardware wallets and JSON are commented out). The seed import reaches the same picker with the same automatic add (`SeedPhraseImportScreen.tsx:90-101`). View-only import has no picker (`ViewOnlyAccountAdderScreen.tsx:122-123`). Only the Ledger flow, unreachable from the UI now, opens the picker with no automatic add (`main.ts:1183-1188`).
- The recovery-v0 prototype touched neither the picker nor onboarding; it added a settings screen and a sidebar entry only.

## 4. Which signing paths fail for a key at privilege value `1`?

**On chain, one path: EIP-1271 verification of an unprotected signature.** No gate in the account tests for exactly `1`. Every other gate tests for non-zero, and `isValidSignature` tests for "greater than 1" only when the signature is unprotected (a raw 65-byte signature or mode byte `00`), so a key at `1` verifies under EIP-1271 only in Standard mode (mode byte `01`, the signature over `AmbireOperation(account, hash)` in the Ambire domain). A key at `2`, the wallet's own default for a smart account key, and a key at a hash pass every gate. **In the wallet, the paths do not read the chain's privilege at all**: they read the local list `account.associatedKeys` and the local flag `key.dedicatedToOneSA`, so a key the wallet did not derive at the smart-account offset is refused for EIP-712 whatever its privilege is.

| Path | Where the check lives | What it checks | Key at `1` | Key at `2` or a hash | Why |
| --- | --- | --- | --- | --- | --- |
| Key offer, every path (wallet) | `signAccountOp.ts:1455-1457`, `:439-444`; `src/web/modules/sign-message/screens/SignMessageScreen/SignMessageScreen.tsx:82`; `src/controllers/keystore/keystore.ts:990-992` | The key is in the keystore and its address is in `account.associatedKeys` | Offered if listed | Offered if listed | A local list; on-chain privileges are read into `accountState.associatedKeys` only to detect the EntryPoint marker (`accountState.ts:77-81`, `:118-127`) |
| EIP-191 message on a v2 account (wallet) | `src/libs/signMessage/signMessage.ts:498-552` | `key.dedicatedToOneSA`: true gives unprotected `00`, false gives an `AmbireOperation` typed-data signature with `01` | Passes (Standard) | Passes | The mode comes from the flag, not from the chain (`:540-551`) |
| EIP-712 typed data on a v2 account (wallet) | `signMessage.ts:554-634` | Throws "does not have privileges to execute this operation" unless `key.dedicatedToOneSA` (`:604-609`); otherwise unprotected `00` (`:632`) | Fails when the key is not flagged | Fails when not flagged, passes when flagged | A local flag set by the derivation index (`keyIterator.ts:164`, `:203`; `account.ts:197-198`) |
| EIP-1271 `isValidSignature` (contract) | `contracts/AmbireAccount.sol:254-262` | `uint(privileges(recovered)) > (usedUnprotected ? 1 : 0)` | Fails unprotected, passes Standard | Passes both | The one gate where `1` and "more than `1`" differ |
| Post-sign verification (wallet) | `src/controllers/signMessage/signMessage.ts:211-238`, `signMessage.ts:369-471` | `UniversalSigValidator` deployless: EIP-6492, then EIP-1271, then `ecrecover` | As the 1271 row | As the 1271 row | The wallet throws when the chain answers false |
| Transaction: `execute` (contract) | `AmbireAccount.sol:156-171` | `privileges(signer) != 0` before and after the batch | Passes | Passes | Non-zero test; unprotected allowed |
| Transaction: `executeBySender` (contract) | `AmbireAccount.sol:187-192` | `privileges(msg.sender) != 0` | Passes | Passes | Non-zero test |
| Transaction signing (wallet) | `signAccountOp.ts:1807-1814`, `:1947-1957`; `signMessage.ts:475-496` | None: Standard `01` over the execute hash | Passes | Passes | No key check |
| User operation signing (wallet) | `signAccountOp.ts:1925-1934` (standard), `:1935-1945` (7702) | None: Standard `01` over `AmbireOperation(account, userOpHash)`, or unprotected for 7702 | Passes | Passes | No key check |
| First bundler deployment, EntryPoint authorization (wallet) | `signAccountOp.ts:1869-1883` | Reuses the EIP-712 path | Fails when the key is not flagged | Same | The flag again |
| User operation validation (contract) | `AmbireAccount.sol:301-324` | `privileges(msg.sender) == 0x7171` for the EntryPoint; `privileges(signer) != 0` | Passes | Passes | Non-zero test |
| Externally validated signature, mode 255 (contract) | `AmbireAccount.sol:147-154`, `:349-352` | `privileges(signer) == keccak256(abi.encode(validator, data))` | Fails | Passes only with the exact hash | The one hash-bound gate |

Two facts follow. A hash privilege on a key whose private key is known does not restrict that key: every ECDSA path passes a non-zero privilege, so the hash-bound gate binds only when the address has no known private key (the wallet's DKIM recovery derives such an address from the last 20 bytes of the hash, `src/libs/dkim/recovery.ts:40-45`). And the wallet's default smart account key sits at `2`, not `1` (`accountPicker.ts:1093-1095`, `keystore.ts:102-105`), so a `1` never appears in a wallet-made account unless a setup writes it.

The 7702 case: a listed basic account with an internal key on Sepolia is handled as an EOA7702 (`src/libs/account/getBaseAccount.ts:17-23`, `account.ts:340-351`, Sepolia listed in `src/consts/7702.ts:16`). Its implementation answers privilege `2` for the EOA itself and the marker for the EntryPoint (`contracts/AmbireAccount7702.sol:16-23`), so the EOA's raw signatures pass EIP-1271 and `executeBySender`. The send path of #16 found the broadcast rule, confirmed at `EOA7702.ts:130-158`: with a native fee and a non-zero portfolio amount the account broadcasts by itself (one call as a plain transaction, several calls as `executeBySender` when delegated, or a type-4 delegation when not); it goes through the bundler when the portfolio's native amount reads zero, when the operation is sponsored (`signAccountOp.ts:935-937`), or with a token fee. The zero-amount case comes from the portfolio, not the provider (`signAccountOp.ts:540`), so it can hold right after a deposit before the portfolio refreshes.

The recovery-v0 prototype set privilege `1` everywhere (`PRIV_AUTHORIZED`, library 250bcab83 `recovery.ts:122-126`) and its "Prove it" step showed a key at `1` moving funds through `executeBySender` (`recovery.ts:834-848`); no key at a hash signed anything there.

Observed on Sepolia (read-only):

The same probe overrode the account's code with the runtime read from the Sepolia implementation and set `privileges` to `keyA: 2`, `keyB: 1`, `keyC: H` (a keccak hash), `keyE: 0`, then asked the chain with `eth_call`:

| Key (privilege) | `isValidSignature`, raw 65 bytes | raw plus `00` | Standard `01` | `execute` Standard `01` | `execute` raw plus `00` | `executeBySender` as caller |
| --- | --- | --- | --- | --- | --- | --- |
| keyA (`2`) | valid | valid | valid | | | |
| keyB (`1`) | invalid | invalid | valid | success, 58910 gas | revert `SV_USED_UNBOUND` | success, 27123 gas |
| keyC (hash) | valid | valid | valid | success, 58935 gas | | success, 27111 gas |
| keyE (`0`) | invalid | invalid | invalid | revert `INSUFFICIENT_PRIVILEGE` | | revert `INSUFFICIENT_PRIVILEGE` |

The EIP-191 digest of "kohaku poc d316" gave the same pattern for keyB (raw invalid, Standard valid) and keyC (both valid). The chain therefore agrees with the source on the one gate that differs for `1`, and it refuses unprotected `execute` signatures for every key, which the source in the tree does not.

## Beside the four questions: the build crashes at load

The production build of `dev/wonderland` at 2f91323db (`yarn build:web:webkit`, exit 0) shows "Something went wrong, but your funds are safe!" with `TypeError: Cannot convert a BigInt value to a number at Math.pow` on every route, the get-started screen included. The cause is `src/web/modules/social-recovery/sdk-doubles/setup-client.ts:52`, `const MAX_WAIT_FIELD = 2n ** 48n`, which Babel compiles to `Math.pow(2n, 48n)` (in the bundle `d875.js`), and the doubles load with the routes. It has been there since the doubles landed (PT-035, squash commit aa2c4b196). The runs above used a copy of the build with that one expression replaced by the literal `281474976710656n`; the repository was not changed. The build gate every PR passes does not catch it, because the build succeeds and only the load fails. A written form `1n << 48n` or the literal fixes it; the display lane met the same Babel behaviour on 2026-09-28 and wrote `1n << 511n`.

## Gaps against the tasks

- PT-042, the create door's picker: the picker opens on create but lists basic accounts only; the smart account, its controlling key and the badge the task asks for need the commented "Smart accounts" section brought back and a default selection the controller does not make today (`selectNextAccount` skips smart accounts). Both changes are in the extension's own picker and in `accountPicker.ts`, so PT-042 keeps its kohaku-commons PR.
- PT-051, the arming save: (a) the sign controller refuses a batch with a call to the account itself (`CALL_TO_SELF`), so the authorization write cannot pass the sign screen without a library change, either the selector exemption of recovery-v0 or a sign type of its own; (b) on Sepolia the account's controlling key at the offset is a keystore key but not a listed account, so it cannot be the payer the wallet offers; the only landing route is a listed basic account paying through `deployAndExecute` (the `byOtherEOA` path), which the chapter's sentence "its controlling key sends them and pays their gas" does not describe; (c) the deployment prepend the chapter asks for is what `deployAndExecute` already does on that route, so the extension prepends nothing itself, it leaves the account undeployed and lets the factory call carry it; (d) the send path of #16 queues calls for a listed basic account only and refuses the offset key as `not-wired`, which is the same limit.
- Signing repair (PT-075 and the fast track): a key the setup writes at `1` verifies under EIP-1271 only in Standard mode, and the wallet signs EIP-712 with a key only when that key is flagged `dedicatedToOneSA`; a recovered key the wallet imports by private key is not flagged.

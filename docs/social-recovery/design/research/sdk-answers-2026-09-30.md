# The sdk owner's answers of 2026-09-30

Received by the owner from @0xAaCE on 2026-09-30 and pasted to the coordinator; every item is decided on the SDK's side (the rulings are dated in the SDK's own `extension-2026-09-30.md`; the real names merged there at 3f6b360).

1. Privacy levels: two in v1, Private (backup `encrypted`, the default) and Public (backup `clear`); `BACKUP_CHOICES` also has `empty`. Shape visible is deferred to a later version: two radios, the third out.
2. Wait ceiling: 30 days; the contract has no ceiling (`uint48 wait`); the SDK refuses above it with `wait.above-maximum` and the field width with `wait.field-width`; `ClientConfiguration.maxWait` (seconds) beside `defaultWait` (48 h), `shortWait`, `requestWindow { default, floor, ceiling }`, `cancelWindow`, `ruleCostBound`; no `DEFAULT_MAXIMUM_WAIT` constant yet.
3. Test challenge before a setup: the extension keeps its own, with its own domain type so a test signature can never be mistaken for a real approval; the SDK adds no member. The passkey config holds only the P-256 public key and `sha256(relyingPartyId)`; the SDK stores no credential id (optional `allowCredentials` at signing, discoverable otherwise); the backup payload carries method, config, optional salt, wait and the pause flag only. The credential id and the ceremony's facts live in the extension's storage.
4. Other doors: the SDK does not list an account's privilege holders; the extension lists them with its own account code. Helpers: `IEventManager.privilegeFilter()`, the `privilege-changed` notification, `IRecoveryActionInteractor.isAuthority(key)` and `holdsAnyPrivilege(candidate)`, `SetupDescription.removedKey`. A counterfactual account's doors are what its creation code privileges. The chapter's sentence that the SDK returns the list will be corrected.
5. Fit check without code: an address with no code is not refused; with `ClientConfiguration.accountImplementation` set the fit is judged against it (a mismatch refuses `action.unsupported`); without it the warning `action.fit-unchecked` and the commit proceeds. Pass `accountImplementation`.
6. publicMetadata: `DraftPrivacy.publicMetadata: Hex` on the draft; `prepareCommitSetup(draft, password?, options?)` copies it into `commitSetup`; always `0x` in v1; no format defined until Shape visible.
7. Failed description and the key count: `candidateKeys` is the configured list (`ClientConfiguration.candidateKeys`), each with its `isAuthority` answer. When the single key a recovery would remove cannot be named (the read failed, or more than one key in control) the save is blocked with the reason on screen; a failure of the informational other-doors read only shows the "cannot see every door" line and leaves the save enabled. `RemovedKey` will gain values naming the two blocking cases; until then a `describeSetup` failure or a key count other than one is the blocking case.
8. The self-call: the account calls itself with `setAddrPrivilege(KIT_SLOT, keccak256(abi.encode(action, "")))`, `KIT_SLOT = address(uint160(uint256(keccak256(abi.encode("kit", action)))))`, inside the same batch as `commitSetup`; in code `IRecoveryActionArming.armingCall()` returns a `PreparedCall` with `sender: 'account'`; the action address is `DeploymentDescriptor.action`; `auditedActions` lists the audited actions. The wallet exempts exactly this call and nothing else: target = the account itself, function `setAddrPrivilege`, slot and value recomputed from an action in `auditedActions`, only inside a batch that also carries `commitSetup`; no danger warning for that exact call; every other self-call keeps the refusal; no on-chain allowlist.
9. confirmSetup: the record is `{ landed, nonce, setupCommitment, isAuthorized, position? }`; it will gain a cause separating "no event at that nonce yet" from "an event with another commitment"; until then, on `landed: false` after a receipt, read again once at the watch tag, then show the disagreed-commitment failure.
10. Real names (merged at 3f6b360): `DeploymentDescriptor { chainId, manager, methodEcdsa, methodPasskey, methodAadhaar, methodZkpassport, action, servedImplementation, deployedAt, digestVersion, managerVersion, shippedMethods, auditedActions }`, `CreationRecord { factory, bytecode, salt, block }`, `BlockTags { read, watch }` over `NAMED_BLOCK_TAGS = ['latest', 'finalized']`, no default descriptors exported yet; `ClientConfiguration { defaultWait, shortWait, maxWait, requestWindow, cancelWindow, ruleCostBound, creation?, accountImplementation?, candidateKeys, blockTags, logChunkSize, tokens, simulate }`; `VERDICTS = ['satisfied', 'rejected', 'not-judged']`; `ValidationResult { errors, warnings }` each `{ code, subject, values }` with the setup error codes `rule.empty, clause.empty, rule.all-thresholds-zero, clause.threshold-above-count, clause.threshold-too-wide, rule.too-wide, credential.duplicate, wait.field-width, wait.above-maximum, action.unsupported, backup.too-wide` and warnings `clause.single-point, clause.threshold-zero, clause.shared-failure, clause.secondary-only, method.unshipped, method.no-declaration, method.stopped, action.unaudited, action.fit-unchecked, manager.already-armed, setup.wait-short, setup.wait-zero, backup.clear, backup.empty, rule.repeated-person` (request, proof, handover, payment and cancel codes in the same file); restore causes `restore.no-backup, restore.backup-unopened, restore.commitment-mismatch`; `AddResult` outcomes `filed | refused` with causes `kind-or-version-unread, binding-mismatch, digest-mismatch, place-unknown, credential-mismatch`; method failures `device-refused, device-unavailable, material-rejected, method-unsupported, request-unsupported`; `KitError` known `{ source, name, selector, args }` or unknown `{ selector?, data }`; thrown refusal errors have no declared property names yet.
